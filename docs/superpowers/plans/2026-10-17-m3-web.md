# M3 Web 端实施计划（server + web）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 落地 M3：新增 `packages/server`（REST + SSE）与 `packages/web`（React SPA），浏览器完成 M1/M2 全部操作（会话列表、流式对话、工具卡片、plan 审查、审批、steer/中断、用量展示）；**worker/task agent 工作时自动打开页面右侧面板展示工作状态**（任务、档位、当前工具、运行/完成/失败）；断线重连 SSE 从日志补发、事件不丢；CLI 与 web 可同时观察同一会话。

**Architecture:**

- **事件总线 = JSONL 日志 tail + turn 迭代器透传**。server 为每个托管会话挂一个 tailer（字节偏移跟踪 + fs.watch/轮询兜底）把日志事件推给全部 SSE 订阅者（天然支持重连补发与 CLI/web 同观察）；web 端驱动回合时，server 迭代 `runMainTurn`，额外透传增量类瞬态事件（text delta、turn 起止、plan 阶段、agent_spawn、approval 请求）。durable 事件只走日志一条路径，杜绝双源不一致。
- **审批桥**：server 侧 `ApprovalChain` handler 与 `onPlanApproval` 回调把请求 park 在 pending 表中并广播 `approval` 事件，REST 端点携带 decision 返回后 resolve promise（CLI 的终端 handler 同款思路换成 SSE/HTTP）。
- **右侧面板数据源**：worker/task 的内联 turn 事件本已全量落盘（M2 决策），tailer 按 `agentId` 过滤即得每个子 agent 的实时工作状态，无需改编排层执行路径；仅给 `runMainTurn` 补上 `agent_spawn` 流变体生产者（M2 遗留 TODO）。
- web 为 React SPA（会话列表 | 对话流 | 右侧 agent 状态面板三栏），状态归约为纯 reducer（可单测），静态资源直接使用仓库根 `public/`（Vite `publicDir` 指向，不搬迁文件）。

**Tech Stack:** Node ≥22 TS（erasable-syntax-only）、Hono（HTTP+SSE）、React 18 + Vite 6、vitest、biome、zod（请求体校验）、`@hotpot/ai` 的 `scriptedAdapter` 回放测试。

**Spec:** `docs/archive/02-architecture.md` §3（server/web 定位）、`docs/archive/04-roadmap.md` M3 节（验收标准）、`docs/PRD.md` 功能需求 7（Web 端）。用户追加需求：静态资源在 `public/` 下；workagent/taskagent 工作时打开右侧面板展示工作状态。

## 计划级决策（对 spec 有意的裁剪，均记录于此）

1. **worker/task 过程可见性走日志 tail，不改 `run-worker.ts`/`spawn-tasks.ts`**（对应 M2 计划决策 3 的 "M3 SSE 可回放补齐"）。右侧面板按 `agentId` 聚合 tailer 事件；子 agent 无文本 delta（日志只存完整 assistant_msg），M3 接受。
2. **UI 事件协议分两类**：`kind:"log"`（durable，带日志事件 id，客户端按 id 去重）+ 瞬态事件（`delta`/`turn`/`plan`/`spawn`/`approval`，无 id）。durable 事件永远只由 tailer 产出，迭代器只产出瞬态事件，server 端不做双源去重。
3. **`agent_spawn` 流变体由 `runMainTurn` 生产**（包一层 `runtime.spawn`），CLI 删除自己的 spawn 包装改为渲染流事件（消除双份渲染）；这是 M2 README「已知边界」里留给 M3 的修补。
4. **重连补发**：SSE 事件 id = 单调 seq（server 内存级）。客户端带 `Last-Event-ID`/`?after=` 重连：命中 ring buffer（保留最近 2000 条）则补发其后事件；不命中则**全量重放日志**（客户端按日志事件 id 去重）。seq 仅 server 生命周期内有效，重启后回退全量重放。
5. **审批无超时**：pending 直到 HTTP 应答或会话销毁；客户端断线重连后凭 requestId 仍可应答。
6. **web 不引状态管理库与 markdown 依赖**：对话态为纯 reducer；markdown 用自研子集渲染器直接产出 React 元素（不使用 `dangerouslySetInnerHTML`，规避 XSS）。
7. **e2e 分层**：API/流程层用 `scriptedAdapter` 自动化（覆盖 M1/M2 场景）；浏览器层按用户 AGENTS.md 约定用 kimi-webbridge 对 dev server 做冒烟（建会话、发消息、右侧面板出现），跑通即可，不追求浏览器内自动化全场景。
8. **端口**：默认 4573，env `HOTPOT_PORT` 覆盖；server 同时托管 web 构建产物与 `/` 静态资源（无构建产物时仅 API，开发态由 Vite dev + proxy 接管）。

## Review Focus

1. **SSE 双源顺序**：tailer 与迭代器事件并发进入广播，seq 以广播时刻定序——同一 tool_call 的 `log` 事件晚于对应 `delta` 是无害的（客户端以 log 为准锚定）。Task 4 集成测试钉死事件序列。
2. **重连不丢**：tailer 基于字节偏移，补发路径（ring buffer / 全量重放）与活跃订阅共用同一广播入口——Task 2 单测覆盖偏移续读，Task 4 集成测试覆盖断线补发。
3. **CLI/web 同观察**：web 不在驱动回合时 tailer 仍全量推日志（含 CLI 侧的 tool_call/approval 审计事件）；server 驱动时 CLI 看不到 delta 属预期（瞬态事件仅服务端产生）。文档写明该不对称。
4. **审批并发**：同一时刻同会话最多一个 pending tool approval（turn 内串行）+ 一个 pending plan；pending 表按 requestId 隔离，REST 应答与广播不竞态（先广播后 park 的写法要避免——实现时 park 先于广播返回）。
5. **tailer 生命周期**：会话打开即启动、销毁即停止；多订阅者共享单 tailer；watch 失败退化为轮询，绝不抛进订阅循环。

**Interfaces（REST 契约，body 均 JSON）：**

- `POST /api/sessions/:id/steer` `{content}` → 202
- `POST /api/sessions/:id/cancel` → 202
- `POST /api/sessions/:id/approvals/:requestId` `{decision:"allow"|"deny"}` → 200/404
- `POST /api/sessions/:id/plan` `{decision:"approve"|"reject"|"annotate", note?}` → 200/404
- `GET /api/sessions/:id/usage` → `{total:{input,output},byTier:Record<tier,{input,output,count}>,byAgent:Record<agentId,{input,output}>`}`（由 `loadSession `折叠`assistant_msg.usage`）
